# Audit complet — juillet 2026

Audit croisé (backend + frontend) réalisé avant l'ouverture de la recette web.
**Bilan : 6 constats critiques, 15 majeurs, ~20 mineurs — tous les critiques et
majeurs corrigés, mineurs corrigés sauf mention contraire.**

## Méthode
- **Backend** : relecture intégrale de `packages/api`, `packages/db`,
  `packages/validators`, `apps/server` — sécurité/autorisations, fuites de
  données privées, injection SQL, logique des transactions QR, robustesse.
- **Frontend** : relecture intégrale de `apps/mobile-web` + vérification
  exhaustive des clés i18n FR/EN (dynamiques comprises), hooks React,
  compatibilité web/native, UX d'erreur.

## Critiques (tous corrigés ✅)

| # | Constat | Correction |
|---|---|---|
| C1 | `listings.byId` (public) exposait **email, GPS exact et stripeAccountId** du vendeur via la relation profil | Projection publique stricte (`lib/publicProfile.ts`) partout où un profil est joint |
| C2 | Auth « dev » active par simple absence de config Supabase (bypass total si `NODE_ENV` oublié) | Opt-in explicite `ALLOW_DEV_AUTH=1` requis, en plus de `NODE_ENV !== production` |
| C3 | `chat.conversations` exposait email/GPS/Stripe de l'interlocuteur | Projection publique |
| C4 | `offers.forListing` exposait email/GPS/Stripe de chaque offreur au vendeur | Projection publique |
| C5 | Une offre **vide** partait à 0 € et court-circuitait le séquestre (`amountCents=0` → statut `escrowed` direct) | Bouton désactivé si montant invalide + validator `amountCents ≥ 1` (un pur trade omet le montant) |
| C6 | Onglets Messages/Portfolio bloqués en erreur 401 après connexion (cache jamais invalidé au changement de session) | Requêtes gatées par `enabled: !!session` + `AuthCacheReset` (vide le cache react-query à chaque changement d'utilisateur) |

## Majeurs (tous corrigés ✅)

- **Double vente** : accepter une 2ᵉ offre sur une annonce déjà réservée était
  possible → `respond` exige `listing.status === "active"` et refuse
  automatiquement les autres offres en attente ; `createFromOffer` exige le
  statut `reserved`.
- **Courses concurrentes transactions** : index unique `transactions.offer_id`
  (+`onConflictDoNothing`) contre la double création ; complétion enveloppée
  dans `db.transaction` avec update conditionnel `status <> completed` —
  plus de double incrément de réputation en cas de scans simultanés.
- **`tradeItemIds` non vérifiés** : appartenance à la collection de l'offreur
  désormais contrôlée ; `parentOfferId` validé (même annonce).
- **Coordonnées GPS des annonces** : arrondies à ~1 km à la création et
  **jamais renvoyées** par l'API (`stripCoords` sur create/update/byId/search) ;
  seule la ville + la distance sont exposées.
- **`profile.byUsername`** : liste blanche de champs (fini le `stripeAccountId`).
- **Bait-and-switch** : une annonce non-`active` n'est plus modifiable ;
  l'invariant carte/scellé est re-vérifié à l'update.
- **Chat > 200 messages** : les 200 plus récents (desc puis remis en ordre) au
  lieu des 200 plus anciens ; conversation acheteur×annonce réutilisée au lieu
  d'en créer une à chaque message ; création transactionnelle.
- **Courbe de portfolio fausse** : réécriture SQL — calendrier `generate_series`
  + jointure latérale « dernier prix connu ≤ jour » (report de cote) +
  agrégation des quantités par variante (plus de dents de scie ni de sous-évaluation).
- **Paywall contournable** : `prices.history` applique désormais le même verrou
  6M/MAX que le portfolio.
- **Fil de conversation non scrollable** : ScrollView + KeyboardAvoidingView.
- **Géoloc web** : try/catch + `reverseGeocodeAsync` sauté sur web (non supporté).
- **Succès invisibles** (publication d'annonce / ajout collection) : message
  affiché hors du bloc démonté.
- **Clés i18n** : `listingDetail.countered`/`withdrawn` ajoutées FR+EN (seul trou).

## Mineurs corrigés ✅
Flags de validation renommés (`iValidatedOther`/`otherValidatedMe`) et
`stripePaymentIntentId` retiré de la réponse ; `acos` borné (−1..1) ; devise du
delta portfolio (€/$) ; distance « 0.0 km » masquée sans géoloc ; erreurs
affichées sur toutes les mutations ; lien connexion sur l'onglet Messages ;
`detectSessionInUrl` activé sur web (confirmation email) ; hydratation unique du
formulaire profil ; message d'erreur auth réinitialisé ; polling stoppé sur
transaction terminée ; `FEE_CENTS` robuste au NaN ; retry sur collision de
pseudo + erreur `CONFLICT` propre ; filtres fantômes `gameId`/`setId` retirés ;
CSV protégé contre l'injection de formule ; static server : comparaison de
chemin avec séparateur + handler d'erreur de stream ; body limité à 1 Mo +
rate limiting 300 req/min/IP sur /trpc.

## Mineurs assumés (v1, non corrigés)
- Quotas free (250 items / 1 alerte) en check-then-insert non atomique : un
  dépassement par requêtes parallèles reste possible à la marge.
- `prices.history` sans filtre moyenne toutes les variantes d'une carte
  (préciser langue/état/foil côté client pour une cote exacte).
- Rate limiting en mémoire : à remplacer par Redis si multi-process.

## Points positifs relevés par l'audit
Aucune injection SQL (fragments `sql\`\`` tous paramétrés) ; mutations filtrées
par `userId` partout ; le code QR de l'autre partie n'est jamais exposé ;
toutes les routes de navigation existent ; export CSV correctement gardé
derrière `Platform.OS === "web"`.
